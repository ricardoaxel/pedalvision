2D true-scale guitar pedalboard planner. Web app, desktop + mobile responsive.

## Session protocol (MANDATORY)

1. Read `docs/progress.md` → find the current task.
2. Read the task file in `docs/tasks/` — it lists exactly which files/sections to read. Read **only** those.
3. Do the task. Verify its acceptance criteria by running them. Then run the **code review** (light model; see below) before opening the PR.
4. Update `docs/progress.md` (done / next / blockers) — this is the handoff memory for the next session.
5. One task per session. **One PR per task/session — exactly one, never multiple (owner instruction, 2026-10-16).** A session opens a **single** PR for its task: no second/rider/split PRs (fold everything the task needs into that one PR; if it needs more, that's a new task in a new session). Commit per task (conventional commits). **Catalog-batch exception (owner-approved, 2026-10-21):** P5 catalog batches are independent tasks — each batch agent gets its own task/session, branch/worktree and **exactly one PR**. A coordinator session may run up to 3 batch sessions in parallel but opens no batch PR itself; each batch copies `docs/tasks/P5-batch-template.md` to its own task file. The one-PR rule still applies per session, not per P5 phase.
6. **Owner-blocked tasks STOP the flow (owner instruction, 2026-09-29).** If the next task — or any step of the current task — requires an owner action (GitHub repo, Cloudflare account/secrets, R2 bucket, dataset, permissions, etc. — see `docs/progress.md` → Blockers), **STOP and report to the owner**. Do NOT skip ahead to an unblocked task to "fill the gap". Wait for the owner to complete the required action before continuing.
7. **Blockers always ship with full, concise owner instructions (owner instruction, 2026-09-29).** For every owner-blocker you report, write the complete step-by-step instructions for the owner — exactly what to click/create/enter, in order, in plain language — but keep them as short as possible. Every step must be actionable and unambiguous (e.g. "create a repo named `pedalvision` (public), then run `git remote add origin <url>` and `git push -u origin main`"). Record them in `docs/progress.md` → Blockers so any future session can re-surface them. When the owner unblocks a task, remove that blocker from `progress.md`.
8. **Design-affecting tasks are gated (owner instruction, 2026-10-12).** If the current task touches design (tokens, theming, colors, typography, spacing, layout, components, or anything visibly rendered in the UI), follow the **Design gate** below. Never hand-tune a palette or restyle on owner feedback without running the designer agent first.
9. **A task is not "done" until its PR is merged (owner instruction, 2026-10-13).** Because every PR requires the owner's approval before merge (below), a task with an open PR is **in review**, not done. While its PR is open: mark it **`in review — PR #N`** in `docs/progress.md`, `docs/roadmap.md`, and the task file; keep **Next** pointing at the same task (pending merge); and do **NOT** start the following task. Do **not** list it under `Done`. When the owner merges, the merge finalizes it: move it to `Done`, advance `Next`, and reconcile the three files in one commit. Rationale: marking a task done while its PR is open contradicts the review-before-merge rule and lets the next session build on unmerged work. (Convention introduced while fixing exactly that contradiction on P0-04 / PR #4.)

## Design gate (MANDATORY — owner instruction, 2026-10-12)

- **The `designer` agent is the design authority** — a staff-level UX/UI expert (`.opencode/agent/designer.md`). Every design-affecting task — tokens, theming, layout, components, canvas visuals, responsive chrome — must be **reviewed by the designer agent before commit**, and its findings folded in. Run it with `/design-review` (optionally `/design-review <PR|propose>`). Rationale: docs/decisions/005-design-governance.md.
- **If the owner does a design task manually** (e.g. "this looks bad, restyle it"), ALWAYS propose to run the designer agent first — never immediately hand-edit colors/tokens. Present the designer's proposal and get the owner's approval before implementing (owner chooses direction; agents do not).
- **New/changed visual directions are owner-approved.** The designer produces the proposal; the owner approves it; only then is it implemented. Record the approval + the direction name in `docs/progress.md`.
- Design PRs must state in the PR description which designer review ran and its verdict, and (for P1+ canvas/UI work) the owner's approval of the direction.
- **Owner-directed simple changes skip the designer/reviewer too** (owner instruction, 2026-10-15) — see Code review → "Owner-directed simple changes skip review". A typo/one-line tweak inside an approved direction needs implementation + the checks, not a design pass.

### Heavy design tasks → designer⇄reviewer loop (owner instruction, 2026-10-12)
- **A "heavy design task"** is any task that establishes or changes a visual direction: a new/redone palette or theme, a new component system, canvas visuals, or a page/chrome overhaul. Small token tweaks / bug-fixes inside an already-approved direction are NOT heavy — the designer review alone (above) is enough.
- **The `design-reviewer` agent (`.opencode/agent/design-reviewer.md`) reviews the actual rendered pixels** — it opens the screenshots with a vision-capable model (default `opencode-go/deepseek-v4.1-flash`), not the code. Run it with `/visual-review <paths|PR n>`.
- **Delegate ALL visual verification to the `design-reviewer` agent (owner instruction, 2026-10-15).** Any time rendered pixels must be judged — PR screenshots, a visual claim, "does this look right" — run the `design-reviewer` (or `/visual-review`). **Never eyeball images with the builder model:** builder models may be text-only and genuinely cannot see pixels, so a builder "description" of a screenshot would be inferred from context/filenames/code, not seen. If you cannot actually see an image, say so and delegate — do not invent a critique. This applies to every UI/canvas task, not only heavy design tasks.
- **Screenshots for the visual review cover desktop AND mobile (owner instruction, 2026-10-15).** Capture and review **both** a desktop viewport and a narrow/mobile viewport for any UI/canvas change, so the responsive chrome + touch layout are actually verified. The P1-03/P1-04 PRs ran desktop-only — that is the **last** exception; from the next design-affecting PR on, a review with only desktop renders is incomplete.
- **One visual review per frozen UI; hard cap ≤2 `design-reviewer` passes per task (owner instruction, 2026-10-15).** Freeze the UI, then run the `design-reviewer` **once**. **Batch every visual finding into a single change**, re-render, and re-run it **only when a fix materially changes the rendered result** (a layout/contrast/touch-visible change) — never per nit, and never for internal refactors or value tweaks inside an approved look (those need the checks, not a review). When a re-run is warranted, pass **explicit questions in one call** instead of reviewing repeatedly. The heavy-loop's 2 iterations count toward this cap. **At the cap with no approval, STOP** and hand the open findings to the owner.
- **Heavy design tasks run a designer⇄reviewer loop of up to 2 iterations (the same ≤2 `design-reviewer` cap above), only after the owner approves running it.** **Every iteration = reviewer feedback (on the rendered pixels) → designer revision → the change implemented in code → re-render (dark + light, desktop + mobile).** A round that only produces comments is NOT a round — implementation is mandatory each time. Stop early only on a reviewer "approve". Orchestrate with `/design-loop` (or step through manually).
- **UX-heavy rework → run the playbook (`docs/design-playbook.md`).** For a task that is *UX/UI-concentrated* — a redesign, "this looks bad / could be much better", a visual overhaul, a new component system, or anything whose deliverable is the experience — follow **`docs/design-playbook.md`** (recall via the `/ux-polish` command, or the auto-surfacing `ux-polish` skill). Its recipe: root-cause the real defects first → designer proposes a **new/bolder** direction (**owner-approved before any UI**) → implement → fold in the UX fixes → expand desktop+mobile Playwright QA → **designer⇄reviewer loop until the reviewer approves, hard cap ~5 rounds** (this playbook's budget **supersedes the ≤2 cap above** for a UX-heavy rework; each round = pixels-reviewed feedback → designer values → code → re-render → commit) → light `/code-review` → one PR, no merge. Rationale: the owner-endorsed P2-01 "Specimen Bench" run (2026-10-17).
- **The loop is gated on owner approval before it starts**, and the final result still goes to the owner for approval. Record iteration count, reviewer verdict, and approval in `docs/progress.md`.
- **Commit per round (owner instruction, 2026-10-13).** Each loop iteration is its own commit (round 1, round 2, …), so the owner can revert to any round ("go back to round X") with a simple `git revert`/checkout. Never squash multiple rounds into one commit.
- The reviewer is authoritative only for *what is on screen*; the designer remains the design authority. If they conflict, present both to the owner.

## Code review (MANDATORY — owner instructions 2026-10-13; revised 2026-10-15 — light model for every pass)

- **Default = ONE pass on the light model (owner instruction, 2026-10-15).** Before a task's PR, the changed **source** is reviewed once by the `code-reviewer` agent on the **light model** (`opencode-go/deepseek-v4.1-flash`, via `/code-review`) — **every** review pass uses the light model (the strong plan-tier model proved too expensive). The test suite is the primary re-check. Rationale: docs/decisions/006-code-review-governance.md.
- **Scope the diff to source only**: `git diff main...HEAD -- src tools e2e .github playwright.config.ts vite.config.ts package.json` — `docs/`, screenshots, and lockfiles are **out of scope**. Hand the reviewer the task-file path, not the repo; it reads only what it needs.
- **Cap the output**: verdict + at most **5** findings (blocker / should-fix / nit) + a one-line round signal. No "what's good" prose. This keeps the review small and the token cost bounded.
- **Fix blockers + should-fixes** (nits only if trivial); then re-run `pnpm lint && pnpm typecheck && pnpm test && pnpm build`.
- **Escalate to the ≤2-pass loop** (`/code-review-loop`, light model) **only when:** the change is high-risk (architecture, security, persistence/serialization, catalog schema, CI/build, new dependencies), OR pass 1 reports a blocker that needs a re-check, OR the owner asks. A pass = reviewer findings → fix in code → re-review; **max 2 passes**, commit each pass's fixes separately (revertible); after pass 2 with blockers/should-fixes open, STOP, tell the owner plainly, and propose more passes.
- **Reuse the reviewer's session for re-checks (owner instruction, 2026-10-15).** A fresh `code-reviewer` subagent starts with an **empty context** (opencode subagents don't inherit the parent), so it re-reads and re-caches the diff/docs — extra tokens. The **first pass** gets a clean slate (that's the independence you want), but a **second/confirmation pass must resume the *same* reviewer session** so it reuses its context and cache instead of paying for a fresh one: with the Task tool, pass the returned `task_id`; on the CLI, `opencode run -s <session-id> …` (capture the id from pass 1).
- **Skip the review entirely** for docs-only / screenshot-only / pure-formatting changes (say so in the PR).
- **Owner-directed simple changes skip review (owner instruction, 2026-10-15).** When the owner asks for a small, low-risk change — or explicitly says to keep it light / skip the reviews — do **not** run the `code-reviewer`, `designer`, or `design-reviewer` at all. Just implement and run `pnpm lint && pnpm typecheck && pnpm test && pnpm build`, then say so in the PR. Examples: one-line/typo fixes, comment/doc tweaks, a small defensive guard, config or CSS value tweaks inside an already-approved direction. When in doubt, ask the owner rather than spending tokens.
- **Re-reviews are conditional, not automatic (owner instruction, 2026-10-15).** After fixing findings, re-run the checks — but run **another reviewer pass only when it's worth it**: the change is high-risk (architecture/security/persistence/serialization/catalog schema/CI/deps), or a *blocker's* fix substantially changed logic. A pass's `FIX AND RE-REVIEW` signal does **not** obligate a second full pass for simple fixes — the test suite is the re-check (and any second pass is the **light** model).
- Record the outcome (passes, verdict, remaining findings) in `docs/progress.md`.
- **Reply in the review thread — never a separate PR comment (owner instruction, 2026-10-15).** When addressing a review finding (Copilot, owner, `code-reviewer`, `design-reviewer`), reply **inside that finding's own thread** and resolve it: GitHub `POST /repos/{owner}/{repo}/pulls/{n}/comments/{comment_id}/replies` (or GraphQL `addPullRequestReviewThreadReply` + `resolveReviewThread`). Do **not** post a separate top-level PR comment summarizing the fixes. One finding → one threaded reply + resolve.
- Scope vs the **Design gate**: the code-reviewer owns code/architecture/security/correctness; the `designer`/`design-reviewer` own visual direction (ADR-005). Both apply when a task touches both — but **the visual check runs only when pixels actually changed**.

- **Run it before changing** `AGENTS.md`, the task **templates/plan docs** (`docs/tasks/P5-batch-template.md`, `docs/tasks/P5-03-pilot-parallel-backfill.md`, `docs/roadmap.md`, `docs/phase-guide.md`, `docs/catalog-backfill.md` process sections), `.opencode/agent/*`, or **starting a parallel wave**. BOSS 209 → **7–9 batches of 24–28 in 3 waves**; **3-wide by default after T-2c/T-2d (no flag)**, logged; the true-token metric remains the budget/stop guard; soft over-usage is logged, hard 2.4M refuses. The first BOSS batch is the token/time calibration; log tokens and minutes per item at every checkpoint.

## Parallel feature + catalog workstreams (T-0b, owner instruction, 2026-10-26)

Full rules + ownership matrix: `docs/tasks/P5-03d-parallel-workstreams.md`; feature tasks start from `docs/tasks/feature-template.md`.

- **In flight:** 1 feature + **up to 3** catalog batches. **3-wide by default after T-2c/T-2d (no flag)**; the feature PR is a **separate 1-PR lane** and does not count toward the catalog 3-PR cap. Default remains serial.
- **Enablement gate:** T-0a merged (true billed metric) + the first T-2 calibration; the owner may waive the calibration.
- **Catalog cap:** ≤3 catalog PRs awaiting owner review (one per batch). **Feature cap:** ≤1 feature PR, separate. At the catalog cap, start no new catalog wave; at the feature cap, start no new feature. Owner merges serially.
- **Budgets (billed non-cache):** catalog 400k/800k per batch; wave 1.6M/2.4M. Feature builder 400k/800k + review ≤300k; task hard ≤1.1M; 6 h. Combined window 2.2M/3.4M; The combined **3.4M hard** is a coordinator-side cross-stream check on top of the wrapper’s fixed 2.4M catalog cap: with a feature active, subtract feature billed spend from 3.4M to get the wave’s remaining catalog allowance. Report the cache-inclusive JSONL floor separately and log by class. **T-2c/T-2d (PR #62) must merge before any 3-wide wave.** The feature PR is separate; 3 catalog + 1 feature = 4 PRs is allowed. At **≥2.0M billed** at a checkpoint, start no new catalog wave; let active batches finish.
- **Ownership:** catalog sessions own raw research + hosted assets + their batch task; feature sessions own feature code/e2e/task; **shared schema/config/docs are coordinator-only**; generated mapped/runtime are never hand-edited.
- **Hard:** a feature session never edits `data/catalog/**`, `public/pedal-assets/**`, `src/catalog/**` or `tools/catalog-*`; a catalog session never edits feature code or `e2e/**`; if a feature needs a shared file, STOP and schedule a serial coordinator task.
- **Merge:** separate worktrees; the owner merges serially; after a catalog merge wait for the verified post-merge build and never hand-resolve generated conflicts.

## Phase gate (MANDATORY)

- When **all tasks of a phase** (per `docs/roadmap.md`) are committed, do NOT start the next phase directly.
- Run a **post-phase code review** in a NEW session on the **light model** (`opencode-go/deepseek-v4.1-flash`) — every review pass uses the light model (owner instruction, 2026-10-15): point it at the phase's merged PRs + `docs/design.md` + `docs/roadmap.md`, and ask it to flag contradictions, gaps, and regressions vs the docs (this replaced doc-only reviews after planning — see ADR-004).
- Fold valid findings back into the docs/tasks **before** starting the next phase.
- Record the review outcome in `docs/progress.md`.
- **Optional user-value review (owner request, 2026-10-19):** the `pedal-user` agent (`.opencode/agent/pedal-user.md`) reviews a phase/feature from the **end user's** perspective (signal chain, connections, power, layout ergonomics, gigging workflow). It is **not** a mandatory gate — propose it to the owner when it matters (e.g. after a phase, or before committing to a feature's direction). Run it with `opencode run --agent pedal-user "<prompt>"` (it isn't in the in-session Task list until a session restart). It advises; the owner decides.
- **Optional performance & cost review (owner request, 2026-10-20):** the `performance-expert` agent (`.opencode/agent/performance-expert.md`) reviews a feature for client CPU/memory/bandwidth/storage cost, Cloudflare free-tier/hosting cost, abuse limits, and free-tier product caps. It is **not** a mandatory gate — run it for performance-sensitive features (canvas scale, share/link payloads, export, storage, bundles) or when the owner asks. Run it with `opencode run --agent performance-expert "<prompt>"` (it isn't in the in-session Task list until a session restart). It advises; the owner decides.

## Hard constraints

- **cm is the source of truth** for all geometry. Pixels exist only at render time: `px = cm × PX_PER_CM × zoom`.
- Apply zoom/pan to the **stage transform only**. Never scale pedal/board objects.
- Images must be same-origin (or CORS-enabled CDN) — cross-origin images break canvas export.
- **Minimal dependencies (owner instruction, 2026-10-12).** The project must stay easy to update and maintain, without constant dependency churn. Prefer **zero new dependencies**; every new dependency (runtime or dev) must earn its place and be justified with a note in the task file or a new ADR. When a dep is unavoidable, prefer ones that are stable/evergreen (small surface, few transitive deps, old code moves slowly) over hot churn. Re-evaluate existing deps for removal when they stop paying for themselves.
- No new runtime dependencies without a note in the task file or a new ADR.
- Do not read whole docs unless the task says so — read the pointed sections only.
- Code, comments, and UI text in English.
- Catalog/image provenance is documented in `docs/decisions/003-catalog-data.md` ONLY. Never reference external dataset sources in code, commits, filenames, or public assets; per-item source URLs live only in catalog data `sources`.
- **Catalog images (owner decision, 2026-10-27 — amends the 2026-10-26 rule):** images are **self-hosted** (`imageSource: "static"` under `public/pedal-assets/`, or the P5-05 CDN) and quality-gated. **Pedal** source hierarchy: **official brand/press/product-support → authorized retailers → user/community with a recorded source → Pedalplayground/planner as a last-resort shipped source (recorded + quality-gated) → our own generated flat art only when none of the above exists/passes**. User/community/planner photos are allowed when the quality gates pass; record the exact source URL. **Resolution is not a rejection reason by itself (owner decision, 2026-10-27):** prefer the highest-resolution **real** source; process it to the 800/350 master (upscaling allowed; default soft ceiling **≤2×** — above that use generated art unless the single contact-sheet pass explicitly accepts the upscale, recorded, and the item stays a counted source gap) and analyze the **final 800 rendition**; the analyzer's `minLongEdge 800` guards that rendition, not the source. Record the source URL, source dimensions and upscale factor in `imageProvenance`; PSNR ≥40 dB is codec fidelity only, so visible softness/halo is a contact-sheet vision check. **Footprint dimensions must come from the official unit/receiver spec, never an accessory;** record the dimension source before applying the aspect gate. **The 31 BOSS legacy items remain `pending-replacement` and must be repaired using the same hierarchy** (official/retailer/community → **recorded planner last-resort** → generated art only if none exists); never keep their old unrecorded planner asset — re-source it and record the exact URL. Boards keep generated flat art by default; planner pixels are never used for boards. **Always record where each image was obtained in the private raw catalog/ledger** (`imageProvenance { kind, sourceUrl, referenceUrl?, status, note }`), never on the public page; planner `last-resort` images are counted as source gaps to improve (`catalog:license-report`, `asset-ledger.md`). Keep `docs/catalog/image-source-registry.md` current (consult it first; append new good sources after a batch). Add the `public-asset` source tag + an attribution/takedown page (P5-01). **Clean-alpha gate:** the final cutout must have crisp alpha with **no white/black/any-colour halo, fringe or jagged edge**; prefer an already-clean top-down transparent PNG and process it with `--matte none` — never re-key a transparent source (a black object on transparent-black corners gets erased). **Analyzer note:** a symmetric trapezoid enclosure (BOSS compact) scores 32–41% on the row-width perspective metric even when flat; the analyzer treats a flat top edge + no skew as a **shape taper** and does not reject. Verify perspective with aspect (≤3% is strong) + the contact-sheet reviewer, never prefer a planner image on the score alone. No bulk copying of descriptions. **2,000 hosted pedals is a hard cap** until P5-05 (image hosting at scale) is decided; pedalboards are a first-class track with their own ~300-file/~20 MB Tier A image budget.
- **Pedalboard catalog assets are our own flat art (owner instruction, 2026-10-25).** New board batches generate a source SVG from the official dimensions/rail layout, sample the body color from the official/authorized reference, and render the 800/350 AVIF. Real photos are **reference only** (proportions/color); their pixels are never shipped. Existing merged seed boards that pass may stay until a repair task. Require bright residual <1%, bright edge <2%, aspect ≤10%, no shadow; the source SVG lives on `main`, the batch PR contains raw + AVIFs + task only. See `docs/catalog/board-art.md`.
- **P5 catalog/data work isolation:** brand/data agents write only `data/catalog/research/{pedals,boards}/<brand>/<batch>.json` (raw) + their own hosted assets under the batch's worktree; `catalog:build` deterministically generates the mapped `data/catalog/{pedals,boards}/...` and runtime `src/catalog/data/{pedals,boards}.json`. They must **never** edit the generated mapped/runtime files or feature code. Feature agents never edit catalog data. Generated catalog builds are **committed** only after a brand PR merges; CI may generate an **uncommitted** runtime into the app workspace for build/Playwright validation. Max **3 batches in flight**; every agent must be observable (`catalog:status`) and stoppable (`catalog:pause/stop`) with per-item checkpoints.
- **Parallel waves launch through `catalog:wave` (owner instruction, 2026-10-25; 3-wide override 2026-10-27).** The coordinator writes a wave plan JSON and runs `pnpm catalog:wave run --plan <file>`. The wrapper starts each batch's runner state + a **supervised** `opencode run` session, **starts up to 3 batches by default after T-2c/T-2d** (`--allow-third` is a deprecated no-op; soft is logged, hard 2.4M refuses), logs the start, and writes `work/catalog/waves/<id>/report.md` (one line per batch + session report backs). The true-token metric remains the budget/stop guard; the third-slot start gate is retired; soft over-usage does not shrink the wave. Never launch batch sessions as raw background `opencode run`s without the wrapper, and never re-read raw logs when the report exists. Each batch session still opens exactly one PR; the wrapper never merges. Token totals in the report cover the root session only — treat them as a **floor** (subagent vision/code-review sessions are separate). **Next-wave protocol:** before a wave, read `catalog:status`, the latest `catalog:wave` report/state, progress, open PRs and post-merge build; classify batches; never redo merged; resume failed/stopped once; pick the next uncompleted batches; after each verified merge refill.
- **Every catalog wave starts in a coordinator session (owner instruction, 2026-10-27).** The next-wave task is the entry point: `docs/tasks/T-3-boss-wave-4.md` (copy `docs/tasks/catalog-coordinator-template.md` for later waves). A fresh "continue scraping" request must use that coordinator task. The coordinator creates the batch tasks/worktrees, runs the token review, writes the wave plan, launches via `catalog:wave`, and opens no PR; each batch agent does one batch/one PR and never launches siblings. Before handoff, the coordinator creates the next wave’s coordinator task from the template and links it in `progress.md`.
- **Parallel feature + catalog workstreams (T-0b, owner instruction, 2026-10-26; updated 2026-10-27):** see the section above and `docs/tasks/P5-03d-parallel-workstreams.md`; one feature task may run alongside up to 3 catalog batches; **catalog cap ≤3 PRs**, **feature cap ≤1 PR (separate)** — 3 catalog + 1 feature allowed.
- **Feature guardrails (owner instruction, 2026-10-27):** every feature PR includes the **feature demo link**, recorded **performance numbers** (bundle delta, picker/canvas frame time, memory, share/export size) against thresholds, and a **docs/feature-catalog update**. No total-count E2E; filter a stable item/brand. These are rules, not separate tasks.
- **NEVER run scaffolding/build tools with `--overwrite`/force flags in the repo root** — `docs/`, `AGENTS.md`, and the PDF are precious. Merge scaffold files manually. (This rule exists because `--overwrite` deleted the entire `docs/` tree on 2026-09-29.)
- **Jack edges require a verified source (owner instruction, 2026-10-25; refined 2026-10-25).** Never infer an `edge` from a sibling model, a “compact layout”, or the enclosure size. Set it only when an official rear/top photo, support page, or **manual diagram — including an image-only/scanned PDF** — shows the connector face; record `jackLayout: { source, confidence: "verified" }`. **Text-layer first:** check the manual text for the panel/connector face; only if it does not name the face, render the panel/connection page with `pdftoppm` and judge a **crop of the connector strip** in the shared contact-sheet/vision step (never one vision call per item). If no official source shows the face, omit the edge (assumed anchors), set `confidence: "unknown"`, and record the one-line reason. A missing PDF text layer is **not** an unknown edge. Large/twin units are not side-jack by default — **the CE-1 and CE-20 Chorus Ensembles have their jacks on the top/rear edge**. `pnpm catalog:check-jacks` gates every batch; `curated.ts` is the only batch-support code file allowed in a batch PR.

## Conventions

- Biome for lint/format — run `pnpm lint` before committing.
- Tests: Vitest for logic (geometry, scale, serialization), Playwright (chromium only) for canvas smoke flows.
- **One PR per task/session (owner instruction, 2026-10-16).** Keep PRs small: **one task = one PR**, and a session opens **only that one PR** — never a second for the same task/session (no rider/split PRs). **Catalog-batch exception (2026-10-21):** each P5 batch is its own task/session/PR; a coordinator runs up to 3 batch sessions but opens no batch PR.

## PR quality standard (MANDATORY — owner instruction, 2026-09-30)

Every PR description MUST include all required sections (currently eight):
1. **Summary** — what changed and why (tie back to the task + roadmap item).
2. **Changes** — files/folders touched and the key decisions taken (incl. any deviations from the task file, and why).
3. **Testing steps** — exactly what was run to verify (commands + their results), plus any manual checks performed. Must map to the task's acceptance criteria.
4. **Screenshots** — attach Playwright screenshots whenever there is a visible UI change (canvas, panels, modals, theming). For P1+ canvas work this is expected on every PR. Use Playwright's screenshot API on the smoke flow and **embed them inline as Markdown images**, e.g. `![desktop dark](https://raw.githubusercontent.com/<owner>/<repo>/<commit-sha>/docs/screenshots/<task>/<file>.png)` — a bare filename/path renders as text, not an image, so listing paths is NOT a screenshot section. Use the **commit SHA** (not the branch) in the URL so the images survive a branch deletion after merge. (Owner instruction, 2026-10-15 — PR #14 listed paths instead of embedding them.)
   **Before/after screenshots are mandatory for any visually visible change (owner instruction, 2026-10-27).** Capture the same viewport, theme and state on the base `main` and on the PR preview; embed both inline with `before`/`after` labels; cover desktop **and** mobile. For interaction/state changes, add a short video/GIF. If there is no prior UI (new feature), show the closest baseline and say why. This is **in addition to** the feature demo link. For catalog image replacements, use before/after contact-sheet crops.
5. **Owner review hints** — the 3 (max) most important, specific things the owner should check before approving. NOT generic advice — the exact risks/edge cases of THIS PR (e.g. "verify rotated-board drop math on an actual device", "confirm the export on iOS doesn't come out blank", "check the new modal closes on Esc + tap-outside"). If fewer than 3 apply, list fewer — never pad.
6. **Review-round digest (owner instruction, 2026-10-15).** Every PR description — and the final session summary to the owner — must include a **one-line-per-round digest** of every review that ran for the task (the `designer`, **each** `design-reviewer` pass, **each** `code-review` pass, and any Copilot review): **reviewer · verdict · what it changed** (fixed / deferred / no action). One line each, so the owner can judge whether each round was worth calling. If no review ran, state that in one line. Keep it terse — it is a ledger, not prose.
7. **Demo share link (owner instruction, 2026-10-25).** Every **batch** PR description must include a read-only `?share=1#s=…` link containing **every item added by that batch**, with illustrative patch cables connecting the items (a simple chain is fine; not a true audio-flow model), and verified board/item/cable counts. Use `pnpm catalog:demo-link --batch <brand>/<batch> --origin <PR-preview-origin>`.
8. **Feature demo link (owner instruction, 2026-10-27).** Every **feature** PR must include a full deployed PR-preview URL (not localhost) that demonstrates the finished feature. Where the state is representable, use a read-only `?share=1#s=…` link with the feature applied (e.g. rotated pedal, routed cable, colored item); otherwise provide the preview URL plus exact steps and a short video/GIF, because share links cannot encode search/modal/export/animation state. Include the final commit SHA, what it demonstrates, and desktop + mobile verification. Screenshots remain required; the demo link is additional.

**PRs are NOT auto-merged (owner instruction, 2026-09-30).** Every PR requires the owner's review and approval before merge. The session prepares the PR to the full standard above and then STOPS and hands it to the owner with the review hints. Sessions must NOT merge their own PRs. The owner reviews (using the hints as a checklist), and either merges or sends it back with feedback.
