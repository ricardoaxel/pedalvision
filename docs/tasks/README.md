# Task files

One file per task. A fresh agent session must be able to execute it reading **only** this file + the files it points to. See decisions/004 for the strategy.

## Format
```markdown
# P#-##: Title
**Phase:** P# · **Status:** todo · **Model:** build-cheap | build-strong | plan
## Goal
The end state, one short paragraph. Not the steps.
## Read first (context pack)
Exact files/sections to read. Nothing more.
## Constraints
What NOT to do / touch / add.
## Steps
Numbered, minimal.
## Acceptance (executable)
Runnable commands or observable checks. ALL must pass.
## Notes
Optional.
```

## Rules
- Scope: 15–45 min of agent work. Bigger → split.
- One concern per task.
- If acceptance criteria can't be written as runnable checks, the task is too vague — refine before starting.
- Model tiers: `build-cheap` (Kimi K2.7 Code / DeepSeek V4 Flash) · `build-strong` (Kimi K3) · `plan` (Kimi K3+).
- When done: update the task Status, update `docs/progress.md`, commit (conventional commits).
- **Code review (light model for every pass — owner instruction, revised 2026-10-15):** before opening the PR, run **ONE** `code-reviewer` pass (`/code-review`) on the **source-only** diff (`git diff main...HEAD -- src tools e2e .github playwright.config.ts vite.config.ts package.json`) on the **light model** (`opencode-go/deepseek-v4.1-flash`) — every review pass uses the light model (the strong plan-tier model proved too expensive). Fix blockers/should-fixes. **Escalate to the ≤2-pass loop** (`/code-review-loop`, light model) only for high-risk changes (architecture, security, persistence/serialization, catalog schema, CI/build, new deps) or if pass 1 reports a blocker. **Skip** for docs-only / screenshot-only changes. **Owner-directed simple changes skip the review entirely** (just implement + run the checks), and **re-reviews are conditional, not automatic** — run another pass only when it's worth it (high-risk, or a blocker's fix changed logic substantially), never for simple fixes. Record the verdict in `docs/progress.md`. See AGENTS.md → Code review + `docs/decisions/006-code-review-governance.md`. **Reuse the reviewer's session for a re-check** (Task `task_id`, or `opencode run -s <id>`): a fresh subagent starts with an empty context and re-caches the diff/docs, so resuming the prior reviewer session is cheaper without losing its independence on pass 1.
- **PR description standard (owner instruction, 2026-09-30):** every PR must include 5 sections — **Summary** (what/why, tie to task+roadmap), **Changes** (files + decisions + deviations), **Testing steps** (exact commands run + results, mapped to acceptance criteria), **Screenshots** (Playwright screenshots whenever there's a visible UI change — required for canvas/panel/modal/theming work; capture **desktop AND mobile** viewports; **embed them inline** as `![alt](https://raw.githubusercontent.com/<owner>/<repo>/<commit-sha>/<path>)` — a bare filename/path renders as text, not an image, and use the commit SHA so the links survive a branch deletion), **Owner review hints** (the 3 max most important, specific things for the owner to verify — exact risks/edge cases of THIS PR, never generic advice, never padded). Also add a **review-round digest** (owner instruction, 2026-10-15): one line per review that ran — **reviewer · verdict · what it changed** — in the PR description and the final summary, so the owner can judge whether each round was worth calling.
- **Visual verification is delegated (owner instruction, 2026-10-15):** whenever rendered pixels must be judged (the Screenshots section, a visual claim), run the `design-reviewer` agent (`/visual-review`) — never judge images with the builder model, which may be text-only. See AGENTS.md → Design gate. State the reviewer's verdict in the PR. **Batch visual fixes and review once per frozen UI (owner instruction, 2026-10-15):** freeze the UI, run `design-reviewer` **once**, batch every finding into a single change, and re-run **only when a fix materially changes the rendered result** — with a **hard cap of ≤2 `design-reviewer` passes per task** (heavy-loop iterations included); at the cap with no approval, STOP and hand the open findings to the owner.
- **Performance-sensitive tasks → optional `performance-expert` review (owner request, 2026-10-20):** for canvas scale, share/link payloads, export, storage, bundle/dependency changes, or before raising a capacity cap, run `opencode run --agent performance-expert "<task + scope>"` before the PR. It reviews client CPU/memory/bandwidth/storage, Cloudflare free-tier/hosting cost, abuse limits, and free-tier caps with current sources. Record the verdict (green/watch/risk/blocker) and applied/deferred findings in the task + `docs/progress.md` and the PR review-round digest. It advises; the owner decides. Not a mandatory gate.
- **One PR per task/session — exactly one (owner instruction, 2026-10-16):** a session opens a **single** PR for its task; never a second/rider/split PR for the same task/session. If more is needed, it's a new task + a new session. **Catalog-batch exception (2026-10-21):** each P5 catalog batch is its own task/session/PR; copy `docs/tasks/P5-batch-template.md` to `P5-03-<kind>-<brand>-<batch>.md`; a coordinator runs up to 3 batch sessions but opens no batch PR.
- **UX-heavy rework → run the playbook (owner instruction, 2026-10-17):** for a task that is UX/UI-concentrated (a redesign, "this looks bad / could be much better", a visual overhaul, a new component system, or anything whose deliverable is the experience), follow **`docs/design-playbook.md`** — recall it with the **`/ux-polish`** command (or the auto-surfacing `ux-polish` skill). Recipe: root-cause the real defects → designer proposes a new/bolder direction (**owner-approved before any UI**) → implement → fold in the UX fixes → expand **desktop + mobile** Playwright QA → **designer⇄reviewer loop until approve, hard cap ~5 rounds** (supersedes the ≤2 cap above for a UX-heavy rework; each round = pixels-reviewed feedback → designer values → code → re-render → commit) → light `/code-review` → **one PR, no merge**.
- **PRs are NOT auto-merged (owner instruction, 2026-09-30):** the owner reviews and approves every PR before merge. Sessions prepare the PR to the full standard, STOP, and hand it to the owner with the review hints — sessions must NOT merge their own PRs. The owner merges or sends it back with feedback.
- **Reply in the review thread — never a separate PR comment (owner instruction, 2026-10-15):** when addressing a review finding (Copilot, owner, `code-reviewer`, `design-reviewer`), reply **inside that finding's own thread** and resolve it (GitHub `pulls/{n}/comments/{id}/replies`, or GraphQL `addPullRequestReviewThreadReply` + `resolveReviewThread`). Do **not** post a separate top-level PR comment summarizing the fixes — one finding → one threaded reply + resolve.
- **Owner-blocked tasks STOP the flow (owner instruction, 2026-09-29):** if the next task needs an owner action (GitHub/Cloudflare accounts, secrets, dataset, permissions), STOP and report what's needed — do NOT skip to another task to "fill the gap".
- **Owner instructions must be full + concise (owner instruction, 2026-09-29):** when reporting a blocker, write the complete step-by-step instructions for the owner — exactly what to click/create/enter, in order, plain language, as short as possible, every step actionable and unambiguous. Record them in `docs/progress.md` → Blockers.
- **NEVER run scaffolding/build tools with `--overwrite`/force flags in the repo root** — `docs/`, `AGENTS.md`, and the PDF are precious. Merge scaffold files manually.
